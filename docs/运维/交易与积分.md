# 交易、订阅、退款与积分运维

只在开启了 `commerce` 之后才需要看这份。涵盖：webhook 持久化摄入、服务商事件应用、履约、订阅命令、退款、权益回收、积分账本和对账。

**金融/服务商状态永远不能靠"信任浏览器"或"删掉失败的行"来修。**

## 定时任务入口

真正被调度的是 `vercel.json` 里的四条，全部要求 cron bearer 密钥，全部 `no-store`：

| 路由                                   | 频率        | 做什么                                                     |
| -------------------------------------- | ----------- | ---------------------------------------------------------- |
| `/api/internal/jobs/commerce`          | 每 5 分钟   | webhook 收件箱、履约任务、订阅/退款命令                    |
| `/api/internal/jobs/reconcile`         | 每小时 :17  | 滞留支付/退款对账、积分账本对账、原始载荷清除、告警快照    |
| `/api/internal/jobs/credit-expiry`     | 每小时 :31  | 预留释放、积分终结、额度过期                               |
| `/api/internal/jobs/account-deletion`  | 每小时 :47  | 账号删除                                                   |

应用实际存在且有效的任务入口只有上表四条：`/api/internal/jobs/commerce`、`/api/internal/jobs/reconcile`、`/api/internal/jobs/credit-expiry` 和 `/api/internal/jobs/account-deletion`。当前 `next.config.ts` 仍保留 `/api/cron/:path*` 的 `no-store` defence-in-depth 规则；这只是静态防御规则，不代表旧的 cron 路由存在。不要恢复或调用已删除的 `/api/cron/*` handler。

worker 必须能并发安全运行。行锁、租约、唯一幂等键和 `SKIP LOCKED` 认领提供串行化边界。

## 核心不变量

- 浏览器价格、结账回跳参数、客户端状态**永远不是**支付权威。
- 签名事件在进入领域之前先归一化；原始请求体最小化保留，且只在有界的加密留存策略下保留。
- `commerce_applied_events` 使用验签后归一化的 `providerEventId`，数据库对「环境 + `providerEventId`」设唯一约束，保证事件应用幂等。
- 订单/支付/订阅/退款在数据库事务里更新，凡是竞争事件可能破坏金额/状态不变量的地方都加行锁。
- 服务商命令任务、webhook 收件箱任务、履约任务都用租约。`processing` 的行**只有租约过期后**才能被重新认领。
- 重试用有界指数退避。达到尝试上限会产生死信/运维可见状态，**绝不当成成功**。
- 已捕获金额是「累计成功退款 + 在途退款请求」的上限。
- `past_due_started_at`、`past_due_grace_ends_at`、`grace_policy_version` 在订阅**首次**进入当前逾期episode 时固定。重复的逾期事件不得延长宽限期。
- **金融成功和权益成功是两件独立的事实。** 如果权益回收无法安全自动完成，就记录对账，而不是悄悄宣布系统一致。

### 结账冲突（HTTP 409）

结账创建对同一笔客户端事务使用稳定的 idempotency key。HTTP 409 可能表示已有 checkout、初始化仍在进行，或需要 operator review 的冲突。收到 409 后，客户端必须保留并锁定原事务语义，进入 review/conflict 状态；不得生成新的 idempotency key 再盲目创建第二个 checkout。运维应先调查已有 checkout 和服务商状态，而不是让用户“再点一次”。

## Webhook 收件箱状态

`payment_webhook_inbox.state`：

- `pending`：已验签、等待应用；
- `processing`：被存活的 worker 认领，直到租约过期；
- `retry`：上次尝试失败，`next_attempt_at` 控制重试时间；
- `completed`：归一事件已应用或已被安全归类；
- `dead_letter`：自动重试已耗尽，需人工调查。

调查死信事件时，**先看**归一化事件、载荷哈希、事件 ID、环境、时间戳和错误码。不要把"解密原始请求体"当成常规调试手段，也不要打日志。

验签失败的 webhook 不得持久化加密/原始的敏感请求体。

## 履约任务状态

`fulfillment_jobs` 是"已确认的金融事实"和"产品权益/积分"之间的持久化边界。

- `pending`：到期可处理；
- `processing`：worker 持有租约；
- `completed`：幂等履约处理器已完成；
- `dead_letter`：自动重试耗尽。

**重置死信履约任务之前，先确认下游权益操作是否已经发生过。** 履约处理器必须有自己稳定的操作/幂等键，这样重试才不会重复发放或重复交付。

积分类商品用下面的积分账本流程，**不要直接改余额**。

## 订阅生命周期

本地投影支持：

```
pending → active → past_due → canceling → canceled → expired → closed
```

激活和续费成功会建立/更新当前付费周期，并清掉当前逾期 episode。一次续费支付会产生一条幂等的 `subscription_period` 记录和一个以服务商支付为键的履约任务。

### 逾期（past due）

首次进入某个 episode 的 `past_due` 时：

- 持久化 `past_due_started_at`；
- **只算一次**并持久化 `past_due_grace_ends_at`；
- 持久化 `grace_policy_version`。

如果之后又来一个逾期 webhook 而这些字段已经存在，**保留原值**。绝不要每次重试/事件都用"现在 + 宽限期"重算。

未来宽限政策变化必须用新的政策版本，且不得追溯延长已固定的截止时间，除非运维执行了显式的评审过的修正。

### 取消与恢复

客户的取消/恢复请求会创建 `commerce_command_jobs`；API 不要求服务商调用同步完成。

同一幂等键的重复客户端请求必须返回/复用原命令，**即使**期间订阅投影状态已经变了。

服务商是否成功由服务商响应/webhook 事实决定。**不要因为用户点了按钮就把订阅改成想要的终态。**

## 命令任务

`commerce_command_jobs.state`：`pending` / `processing` / `completed` / `dead_letter`

命令类型：`subscription_cancel`、`subscription_resume`、`refund_request`

失败时清除租约、递增尝试次数、安排下一次指数退避重试。达到最大尝试次数后保留为 `dead_letter`。

**死信的退款命令还会把该笔退款转入运维对账**，因为服务商是否执行过尚未确定。

## 退款流程

### 请求准入

退款请求必须：

- 属于已认证的留存账户主体；
- 目标是一笔已成功的支付；
- 币种与该支付一致；
- 金额为正、幂等键稳定；
- 对该支付行做串行化；
- 满足 `已捕获 >= 已退 + 在途请求 + 本次请求`。

幂等重试检查发生在**重新占用可退余额之前**，这样重复请求不会把自己卡死。

### 服务商事件应用

一条成功的签名退款 webhook：

1. 锁定支付/订单；
2. 拒绝累计退款超过已捕获金额；
3. 推进支付/订单的退款投影；
4. 尽可能匹配本地退款请求；
5. 要么安排一次安全的权益回收，要么记录对账。

**有歧义的 webhook 不猜**，直接建运维对账记录。

### 全额退款的权益回收

全额退款会安排 `reverse:<fulfillmentKey>`。

对积分履约，**只能**回收来源支付/订阅周期里**未使用**的积分。已消耗或正被预留的积分让全自动回收变得不可能，此时退款转入 `reconciliation_required` 并记录被阻断的条件。

### 部分退款

平台**不发明**"退 30% 就收回 30% 权益"这种通用规则。除非产品有显式评审过的部分回收政策，否则成功的部分退款在金融上成功，权益部分仍需运维对账。

## 对账

`commerce_reconciliation_runs` 是只追加的运维证据。至少在这些情况下使用：

- 无法匹配或有歧义的退款服务商事件；
- 权益回收被"已消耗/已预留"阻断；
- 服务商命令耗尽重试且外部最终状态未知；
- 人工做的服务商 vs 本地状态比对。

每次事件记录：目标类型和稳定 ID、执行方（`worker` / `webhook` / 运维流程）、之前的事实、用于判断的服务商权威事实、之后的目标投影、显式结果（如 `operator_review_required`）。

**绝不要为了让看板变绿而删除对账记录。**

# 积分账本运维

只在开启 `credits` 后需要。**没有可变的余额列，也不授权任何手工改余额。**

## 不变量

- 每次发放恰好一条等量的 `grant` 账本条目。
- 可用余额由「发放 − 终态扣减 − 活跃预留」推导得出。
- 预留精确分配到具体的 grant ID 和数量，且**绝不在产品工作运行期间持有数据库事务**。
- 提交/释放使用原始分配，绝不在终态时重新分配。
- 已交付但积分提交失败的结果**仍然算已交付**。`credit_finalization_jobs` 只重试提交，绝不重跑产品工作。
- 退款/来源回收只碰来源 grant 里未使用的单位。已消耗/已预留的部分报告为被阻断；**绝不动无关的 grant**。

## 排查不一致

改数据之前，先对目标环境跑积分对账。以下问题码按运维可见事故处理：

```
RESERVATION_ALLOCATION_MISMATCH     STALE_ACTIVE_RESERVATION
GRANT_LEDGER_MISMATCH               GRANT_OVERDRAWN
EXPIRED_GRANT_WITHOUT_EXPIRY_ENTRY  CROSS_SUBJECT_ALLOCATION
CROSS_CREDIT_TYPE_ALLOCATION        TERMINAL_RESERVATION_WITHOUT_LEDGER
```

**不要靠改余额来修复。** 保留不可变历史，查清原因后用显式评审过的调整或补偿流程处理。

`credit_reconciliation_incidents` 持久记录每个 `(问题码, 实体 ID)` 的不一致。重复检测会递增 `occurrences` 并刷新 `last_detected_at`；该实体扫描干净后事故从 `open` 变 `resolved`。运维告警只报开放事故的**总数**，绝不包含问题码、实体 ID 或细节。

PostgreSQL 用 `credit_ledger_entries_append_only` 触发器强制账本只追加。应用和运维流程都不得禁用它，也不得直接 update/delete 账本行。修复用评审过的补偿条目，保证原始历史可审计。

## 终结积压

`credit_finalization_jobs`：`pending` 到期可重试 / `processing` 租约过期后才可回收 / `completed` 无需处理 / `dead_letter` 重试前必须调查。

**终结任务的存在本身就证明交付已经持久化了。绝不要从这个队列重跑用户的实际工作。**

## 退款回收

全额回收只能撤销与服务商确认来源关联的 grant 中**当前未使用**的单位。若已消耗或仍被预留，记录并报告被阻断的数量交政策处理。除非项目有显式评审过的换算政策，否则部分回收一律阻断。

# Webhook 原始数据留存

归一化的服务商事实才是运维记录。**原始 webhook 请求体是例外证据，绝不是默认持久化格式。**

## 留存等级

- `normalized_only`：已知且成功归一化的事件，不留原始密文。
- `transient_encrypted`：合法签名事件可为短期运维恢复保留加密原始字节，**必须有过期时间**。
- `unresolved_encrypted`：合法但未解析的事件可为有界调查保留加密原始字节，**必须有过期时间**。
- 法务保留（legal hold）用加密留存行上的 `legal_hold_review_at` 表示。**它不是无限期无人值守留存的许可。**

验签失败的请求不得留存原始密文，也不得留存由不可信请求体推导出的归一事实。

## 数据最小化

已知事件的归一化基于**白名单**。不要把买家邮箱、姓名、IP、授权值、签名、会话/认证令牌、银行卡数据或任意服务商字段写进归一 JSON。

结构化日志必须经过仓库的脱敏边界。**不要记录解密后的原始 webhook 请求体。**

## 加密

例外原始载荷走 `COMMERCE_RETENTION_KEY` 和 `COMMERCE_RETENTION_KEY_ID` 配置的留存密钥路径。密文、密钥标识和过期时间存在一起。**禁止明文原始载荷列。**

密钥轮换按 [密钥轮换](密钥轮换.md) 走。轮换不得让仍在留存期内的密文变得不可解密——旧密钥要保留到其剩余留存窗口结束，或走显式评审过的重新加密迁移。

## 清除流程

由已认证的内部对账任务发起有界清除。选行使用 `SKIP LOCKED` 行锁，多个 worker 可安全并发。

对没有活跃法务保留的过期行，清除会原子地清空 `raw_payload_ciphertext`、`raw_payload_key_id`、`raw_payload_expires_at`，并写入 `raw_payload_purged_at`。归一化的白名单事实和载荷哈希保留，用于幂等/审计。

重复清除是幂等的。**不要为了方便就从日志、备份或其它分析系统里把已清除的请求体捞回来。**

## 法务保留

有活跃 `legal_hold_review_at` 的行会被自动清除跳过。运维必须在记录的复核日期做处理，二选一：

1. 移除/解决该保留，让正常过期继续；或
2. 记录合法/合约理由和一个新的**有界**复核日期。

**绝不能为了逃避调查清除失败而创建法务保留。**

## 可观测性

运维遥测只暴露聚合值：留存原始载荷积压量、最老留存载荷的秒级年龄、验签失败量、worker/任务积压与年龄、死信/服务商失败计数。

**任何 webhook 请求体、买家身份、订单/支付标识、邮箱、令牌、签名或卡数据都不属于这些指标/告警载荷。**

对账任务发出 `webhook_retained_payloads` 和 `oldest_webhook_payload_age_seconds`。达到配置的积压/年龄阈值时触发 `webhook_retention_backlog_stale`。

## 事故响应

留存积压或最老年龄突破阈值时：

1. 确认内部对账调度在跑且鉴权正常；
2. **在访问任何留存密文之前**，先看聚合指标和任务/错误码；
3. 检查法务保留是否解释了被跳过的行；
4. 确定失败模式后才再次运行有界清除任务；
5. 确认密文数量下降且 `raw_payload_purged_at` 已写入；
6. 调查数据库/服务商故障时，**不要把原始载荷复制进工单或聊天**；
7. 怀疑泄露时，只通过密钥轮换流程轮换留存密钥。

## 开启交易前的检查

- `features.commerce.enabled` 且只开启需要的子功能；
- 目标环境的 Waffo 合约/资源已按 [Waffo 合约与验收](../参考/waffo-合约与验收.md) 验证；
- 每个启用商品都有精确的服务商商品映射和不可变的本地价格快照；
- 订阅商品声明了 `billingInterval: "month" | "year"`；
- 每个启用商品都有履约和回收处理器；
- 退款/法律政策事实与实际商业模式一致；
- 定时任务已部署且鉴权正常；
- 迁移通过 empty-to-latest 和 main-chain-to-latest 验证；
- 单元、PostgreSQL 集成、服务商合约、安全、交易、订阅、积分、发布和 E2E 门禁全绿；
- **运维人员在接生产流量之前已经理解死信和对账队列。**

开启积分还要额外满足：commerce 已开启；每个积分商品有显式履约定义；每个履约键映射到真实处理器；数量为正整数；`bun run verify:credits` 通过；目标环境对账报告零个无法解释的问题。

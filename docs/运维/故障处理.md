# 故障处理：死信、回滚、备份恢复

出事了看这份。三个场景：任务卡在死信队列、发布出问题要回滚、数据库要恢复。

---

# 一、死信队列

死信记录是**已经耗尽自动重试**的持久化失败。**不要手工改队列表或业务表。**

队列名：`webhook`、`fulfillment`、`commerce_command`、`credit_finalization`、`account_deletion`

## 查看

用只读的脱敏工具，指定目标环境和该环境的数据库凭据：

```bash
APP_ENV=staging DATABASE_URL="$DATABASE_URL" \
  bun scripts/inspect-dead-letters.ts --environment=staging
```

输出**只有**队列名、内部记录 ID、尝试次数、有界错误码和创建时间。它有意排除了载荷、邮箱、主体 ID、订单/支付标识和服务商载荷。

## 判断重试是否安全

重试之前，以下五条必须全部确认：

1. 底层依赖或配置问题已经解决。
2. 该条目仍是 `dead_letter`——已完成或已重新入队的**绝不能碰**。
3. 重新执行受该队列的幂等键/领域不变量保护。
4. 运维已记录一个**具体的、事后另一个人能审计的**理由。
5. 所选 `--environment` 与 `APP_ENV` 一致，且数据库凭据属于该环境。

生产环境要用批准路径下发的**短期**运维/数据库凭据。**不要把生产凭据留在 shell 历史、工单或聊天里。**

## 重试

```bash
APP_ENV=staging DATABASE_URL="$DATABASE_URL" \
  bun scripts/retry-dead-letter.ts \
  --environment=staging \
  --queue=fulfillment \
  --id=<死信ID> \
  --reason="服务商故障已解决，幂等性已核对" \
  --confirm=RETRY:<死信ID>
```

脚本委托给死信领域操作。该操作**只**把条目从它精确的死信状态转回该队列的可重试状态、清除租约/错误状态，并在同一事务里写一条不可变的 `dead_letter_retried` 审计事件。它**不会**直接改订单、支付、积分、订阅、账号或履约的业务结果。

## 重试之后

再查一次，然后验证对应的定时 worker 和运维告警。

**重试后又回到死信的，需要重新诊断，不要反复强制入队。** 遇到支付/退款不一致或外部副作用不确定的情况，走对账/人工复核，而不是盲目重试。

# 二、发布回滚

回滚是**受控的恢复动作**，不是盲目倒转数据库历史的许可。

## 每次发布前先记录

候选 commit、上一个已知可用的部署、迁移集合、环境/服务商改动、数据库恢复点、任务/schema 兼容性、负责人。在验证完成之前，保留上一个部署的地址/版本。

给这次发布分类：

- **纯代码 / 向后兼容**：旧代码能安全地跑在当前数据库/schema 上。
- **只能向前的 schema/服务商变更**：没有数据库/服务商恢复计划的话，旧代码不安全。
- **凭据泄露**：**绝不为了恢复服务而回滚到一个已泄露的密钥。**

## 代码回滚

1. 如果破坏性/后台操作会放大事故，先停掉或暂停它们。
2. 用部署平台的不可变部署历史，把最后一个已知可用的 commit 提升/重新部署。
3. 迁移向后兼容时，保留当前数据库。
4. 验证 `/api/health/live`、`/api/health/ready`、登录、一个有代表性的公开页面、内部任务鉴权，以及受影响的产品流程。
5. 支付或履约类事故，宣布恢复之前先做交易/积分对账。

## 数据库恢复

**不要对生产执行临时的 down migration。** 确实需要数据/schema 恢复时：

1. 把批准的备份/PITR 点恢复到一个**隔离的**数据库。
2. 跑 `RESTORED_DATABASE_URL=... bun scripts/verify-restored-database.ts`。
3. 确定恢复点之后发生了哪些已在外部落地的服务商事件，以及它们如何重放/对账。
4. 只有到这一步，才在事故/发布负责人的许可下切换应用流量。

具体恢复步骤见下面第三节。

## 服务商/配置回滚

服务商配置改坏了，只有在旧凭据/配置**仍然有效且未泄露**时才恢复它。重新放流量之前，先验证回调来源、webhook 签名、商品 ID 和环境隔离。

## 迁移兼容规则

包含破坏性或非向后兼容迁移的发布，必须走「扩展 / 迁移 / 收缩」式的滚动，或者显式向前修复。**如果上一个应用版本无法安全运行在新 schema 上，它就不是一个合法的回滚目标。**

## 回滚后的验证

跑针对该事故的专项套件，加上：

```bash
bun run typecheck
bun run test:unit
TEST_DATABASE_URL="$TEST_DATABASE_URL" bun run test:integration
bun run verify:security
bun run verify:commerce
bun run verify:credits
bun run build
bun run verify:release
```

事故进行中，如果跑完整套件会拖慢止损，可以先用批准的部署冒烟检查替代；但**关闭事故之前必须跑完整门禁**。

## 记录

触发原因、影响范围、前后 commit、迁移、数据库恢复点、服务商/配置/凭据改动、执行的命令、部署 ID、对账结果、客户受影响窗口、负责人和后续项。**绝不把密钥或私有载荷写进记录。**

# 三、数据库备份与恢复

**只能对隔离的恢复目标执行。绝不要覆盖生产数据库的唯一副本，绝不要把 dump 提交进仓库。**

## 前置条件

- 确认来源环境、数据库属主和批准的留存/PITR 政策。
- 尽量使用短期数据库凭据。
- 确保恢复目标与生产的 worker、webhook、定时任务、邮件/支付服务商完全隔离。
- 记录来源 commit、迁移数量、备份时间戳和负责运维人。

## 逻辑备份

```bash
pg_dump "$DATABASE_URL" \
  --format=custom \
  --no-owner \
  --no-acl \
  --file=creat-web.dump
```

**把这个 dump 当生产数据保护**：静态加密，演练结束后按批准的留存政策删除临时副本。

## 恢复到隔离数据库

```bash
createdb creat_web_restore_test
export RESTORED_DATABASE_URL='postgres://.../creat_web_restore_test'
pg_restore \
  --dbname="$RESTORED_DATABASE_URL" \
  --no-owner \
  --no-acl \
  creat-web.dump
RESTORED_DATABASE_URL="$RESTORED_DATABASE_URL" bun scripts/verify-restored-database.ts
```

验证器会检查迁移历史、Better Auth/核心关系、支付/订阅/积分约束、重复幂等键、积分账本对账，以及按属主隔离的合成读取。**验证器失败会阻断发布和恢复签核。**

## 托管服务商 / PITR 恢复

用托管 PostgreSQL 时，先用它的 PITR 或快照恢复到一个**全新的隔离数据库/项目**。记录选定的恢复时间点、服务商任务/结果和连接目标。**在 `scripts/verify-restored-database.ts` 通过且发布负责人复核过恢复点之前，不要切换应用流量。**

服务商后台具体点哪里、留存时长多久、负责人是谁——这些是部署事实，必须在 staging/生产激活记录里补全，模板发明不出来。

## 恢复验证

冒烟验证器通过之后：

1. 对恢复出来的数据库配置跑 `bun run db:verify`。
2. 在禁用/仅测试服务商调用的前提下，跑登录、交易、订阅和积分的专项集成套件。
3. 确认没有任何生产 cron/webhook 端点指向这个隔离数据库。
4. 用批准的内部运维工具比对预期行数范围；**不要把用户/支付数据粘进工单或聊天**。
5. 记录耗时、结果、异常和清理情况。

## CI 里的恢复演练

CI 会在 PostgreSQL 服务里建 schema/数据、做一次 custom 格式 dump、恢复到另一个数据库并跑 `scripts/verify-restored-database.ts`。这在每次相关改动上都对合成数据证明了仓库的 dump/restore/冒烟流程。

**它不能替代针对具体部署的托管服务商 PITR 演练。**

## 清理

证据记录完成后，删除临时 dump 和隔离恢复库。如果演练暴露了凭据，轮换它，而不是继续复用演练凭据。

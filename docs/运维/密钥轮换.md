# 密钥轮换

**绝不把一个密钥挪作他用。** 每次轮换都记录：环境、密钥用途、新旧密钥标识（如果有）、执行人、起止时间、验证证据、回滚决定、旧密钥吊销情况。

**通用顺序**：创建新凭据 → 服务商支持的话配置重叠期/双重校验 → 部署 → 验证那条精确的依赖链路 → 吊销旧凭据 → 再验证一次。

如果没有双重校验能力，**先准备好回滚部署再切换**。

## Better Auth 密钥

1. 生成新的高熵 `BETTER_AUTH_SECRET`。
2. 除非部署的 Better Auth 版本明确支持多密钥校验，否则**按"会影响所有会话"处理**。
3. 在批准的窗口部署；验证新登录/会话创建、登出和受保护路由。
4. 确认会话失效行为符合预期，评估对用户支持的影响。
5. 只有在回滚不会重新启用已泄露凭据的前提下才回滚。**遇到泄露，走遏制 + 强制重新认证，而不是回滚。**

## Google OAuth 客户端密钥

1. 为现有 staging/生产 OAuth 客户端创建替换密钥，**不要意外改动**已授权来源/回调 URI。
2. 配置新的 `GOOGLE_CLIENT_SECRET`，部署并验证登录/回调/state 处理。
3. 新链路成功之后，才在 Google 侧吊销旧密钥。
4. 只有在确认旧密钥未泄露且仍有效时，才回滚到旧密钥。

## Resend API Key

1. 创建一个受限的替换 key，保留已验证的发件人/域名。
2. 设置 `RESEND_API_KEY`，部署并在 staging 发一封 Magic Link 或测试事务邮件。
3. 验证送达，且日志中不含邮件内容/私有载荷。
4. 吊销旧 key。验证失败就先恢复未泄露的旧 key，查清楚再吊销。

## Waffo 私钥 / API 凭据

1. 为同一环境/商户/店铺创建或获取替换凭据。
2. 设置 `WAFFO_PRIVATE_KEY`，**在交易 worker 受控的情况下**部署，验证商品同步、测试结账和退款读取链路。
3. 服务商认证成功后再恢复正常 worker。
4. 吊销旧凭据；对切换期间尝试过的请求做对账。

## Waffo Webhook 验签密钥

1. 在服务商后台配置替换的 webhook 签名/验签材料。
2. Waffo 支持重叠期时，过渡期部署"新旧都校验"。**不支持重叠期的话，服务商切换和应用部署必须作为同一个变更窗口协调完成。**
3. 发一个签名测试事件，验证：合法接受、非法签名拒绝、去重生效、非法签名不留存原始数据。
4. 服务商确认新签名已生效后，移除旧密钥。

## Turnstile 密钥

1. 按 Cloudflare 支持的方式，为同一 widget/site key 轮换或创建新的 secret。
2. 设置 `TURNSTILE_SECRET_KEY`，部署并验证 Magic Link 在预期 action/hostname 下工作，以及伪造/重放 token 被拒绝。
3. 新密钥生效后才吊销/重置旧校验材料。
4. **绝不把 secret 暴露到浏览器配置里——只有 `TURNSTILE_SITE_KEY` 是公开的。**

## Cron / 内部任务密钥

1. 生成一个新的、独立的高熵 `CRON_SECRET`。
2. 更新 Vercel/项目里用于授权内部定时路由的密钥并部署。
3. 用新 bearer 凭据调一次内部任务，并验证切换后旧凭据被拒绝。
4. 如果调度器是自动注入凭据的，关闭这次轮换之前要验证至少一次真实定时运行，以及未认证时的 401 路径。

## 数据库凭据

1. 创建新的数据库角色/密码或轮换凭据，**只给必需权限**。
2. 在隔离 staging 测试连接/迁移/读写行为。
3. 更新 `DATABASE_URL`，部署，验证就绪探针和一笔有代表性的事务。
4. 所有应用/worker 连接都迁移完成后再吊销旧凭据。**遇到泄露，在遏制允许的第一时间吊销并终止旧会话。**

## 分析 ID / 配置

GA4 measurement ID 和 Clarity project ID 是标识符而非 bearer 密钥，但改动它们会改变数据流向。更新 `GA4_MEASUREMENT_ID` / `CLARITY_PROJECT_ID`，验证同意门控和白名单载荷契约，然后在旧目的地不再被授权时关闭它。

**不要把私有应用数据迁移进分析系统。**

## 演练要求

staging 激活时，必须至少完成一次**一次性凭据**的轮换，并留下回滚/恢复证据，同时把上面每条流程都过一遍。

仓库 CI 会验证配置拒绝和密钥用途隔离，但**它不能代替所有者去创建或吊销真实的服务商凭据**。

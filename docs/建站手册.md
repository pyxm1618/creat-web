# 建站手册

从这个 starter 建一个新站，从零到上线的完整顺序。

其他文档是遇到具体问题才查的参考资料，索引见 [docs/README.md](README.md)。
这份是入口，按时间顺序走一遍，需要深入时再去看那几份。

---

## 零、先理解一件事

这个 starter 给你的是**壳**：SEO、路由、法律页、登录、支付、积分的完整基础设施。
**产品本身要你自己写。**

所以"建站"其实是两件事：

1. 改配置 —— 站名、文案、SEO、法律信息（半天到一天）
2. 写产品 —— 你的工具/计算器/生成器本身（取决于产品复杂度）

第 2 步的代码放 `src/modules/<产品名>/`，详见[产品模块](参考/产品模块.md)。

另外：**所有付费和登录功能默认是关的**，而且关得很彻底——不初始化、不打包、
不要求密钥。先上线免费版、验证有人用、再打开付费，这是这个 starter 的核心设计。

## 一、开始之前要准备的东西

### 立刻需要

- **Bun 1.3.14**（版本锁死，别用别的）
- **PostgreSQL 16**（Mac 上 `brew install postgresql@16`）
- 一个代码编辑器

**注意**：即使你只做纯 SEO 站、不要登录不要支付，`DATABASE_URL` 仍然是必填项。
好消息是功能全关时实际不查库，本地填一个占位连接串就能跑起来。

### 上线时才需要

- **域名**（真实的 HTTPS 域名，不能是 localhost）
- **Vercel 账号**（免费额度够用）
- **一个在线的 PostgreSQL**（Neon、Supabase 等都行）
- **Google Search Console**（提交 sitemap 用）

### 打开付费/登录时才需要

- 登录 → Resend 账号（发邮件）+ Cloudflare Turnstile 密钥（人机验证）
- 谷歌登录 → Google OAuth 凭据
- 支付 → Waffo 商户账号（注意：**不是 Stripe**）
- 统计 → GA4 或 Clarity 的 ID

## 二、跑起来（10 分钟）

```bash
bun install --frozen-lockfile

# 启动数据库（Mac + brew 安装的话）
/opt/homebrew/opt/postgresql@16/bin/pg_ctl \
  -D /opt/homebrew/var/postgresql@16 -l /tmp/pg.log start
psql -h localhost -d postgres -c "CREATE DATABASE my_site;"

# 跑起来
APP_ENV=local APP_ORIGIN=http://localhost:3000 \
  DATABASE_URL="postgres://$(whoami)@localhost:5432/my_site" \
  bun run dev
```

打开 http://localhost:3000 应该能看到默认站点。

## 三、改配置：每次建站必改的文件

全部在 `src/config/` 下。**下面七个文件，一个都不能少。**

### 1. `site.config.ts` — 站点身份

```ts
slug: "my-site",                        // 项目标识，小写加连字符
name: "My Site",                        // 站名，显示在导航和标题里
canonicalOrigin: "https://mysite.com",  // 必须是真实 HTTPS，不能 localhost
defaultLocale: "en",
supportedLocales: ["en"],               // 只加有真实翻译的语言
localeLabels: { en: "English" },
```

### 2. `seo.config.ts` — 全站 SEO 默认值

```ts
defaultTitle: "My Site",
titleTemplate: "%s | My Site",   // 内页标题格式
defaultDescription: "……",         // 150-160 字符，写清楚这站是干什么的
releaseStatus: "draft",           // 上线前改成 "reviewed"，见第七节
```

### 3. `routes.config.ts` — 每个页面的搜索意图 ⭐ 最重要

这是整个 SEO 系统的中枢。每个可索引页面都要写全：

```ts
{
  route: "/",
  class: "public_indexable",
  searchIntent: "用户想解决的具体问题",       // 一句话
  primaryKeyword: "主关键词",
  secondaryKeywords: ["次要词1", "次要词2"],
  title: "标题（会出现在搜索结果里）",
  description: "描述（搜索结果里的那段说明）",
  h1: "页面上的大标题",
  pageType: "WebApplication",              // 或 Article / Pricing / Legal
  relatedRoutes: ["/其他页面"],             // 内链关系
  lastModified: "2026-08-31",
  reviewStatus: "reviewed",
}
```

**一个搜索意图 = 一个页面。** 不要因为关键词是近义词就拆成两页，SEO 闸门会拦。

`class` 的四种值：
- `public_indexable` — 公开且要被搜索引擎收录
- `public_noindex` — 公开但不收录（法律页）
- `private` — 需要登录
- `system` — API、sitemap 等

### 4. `home.config.tsx` — 首页内容

⚠️ **这个文件不在官方那份"6 个文件"清单里，但每次建站都必须改。**

首页由若干 section 拼成，每个都能开关和排序：

```
hero              大标题 + 两个按钮
tool-demo         产品本体（你的工具放这里）
use-cases         使用场景卡片
how-it-works      步骤说明
features          特性卡片
comparison        对比
pricing           价格
faq               常见问题（可折叠）
seo-content       给搜索引擎看的正文
related-resources 相关页面
final-cta         底部行动号召
```

产品本体接在 `tool-demo` 的 `surface` 里：

```tsx
import { MyTool } from "@/modules/my-tool";

{
  type: "tool-demo",
  heading: "……",
  body: "……",
  surface: <MyTool />,
}
```

### 5. `seo-landings.config.tsx` — 内页内容

⚠️ **同样不在那份清单里，但有内页就必须改。**

结构和首页一样，但要注意顶部这几行：

```ts
const guideRoute = indexableRoute("/your-page");
```

这里的路由**必须先在 `routes.config.ts` 里定义过**，否则直接报错。
两个文件要一起改。

### 6. `legal.config.ts` — 法律信息 ⭐ 上线必填

```ts
operator: {
  legalName: "你的公司或个人名义",    // 默认是 "Sample Operator — replace before launch"
  jurisdiction: "所在国家/地区",       // 决定适用哪国法律
  supportEmail: "真实的客服邮箱",       // 用户投诉、数据请求会发到这
},
minimumAge: 18,
dataCategories: [ /* 你收集哪些数据 */ ],
processors: [ /* 用了哪些第三方服务 */ ],
retentionRules: [ /* 数据保留多久 */ ],
releaseStatus: "draft",   // 填完真实信息后改成 "reviewed"
```

这份配置会自动生成六份法律文档：隐私政策、服务条款、可接受使用政策、
退款政策、账号删除说明、联系方式。**内容会根据你开了哪些功能自动调整**——
比如没开支付就不会出现退款条款。

**这是模板不是法律意见。** 面向欧盟用户的话建议找人审一遍。

### 7. `features.config.ts` — 功能开关

第一次上线建议保持全关：

```ts
auth:      { enabled: false, google: false, magicLink: false, password: false },
email:     { enabled: false },
commerce:  { enabled: false, oneTime: false, subscriptions: false, credits: false },
analytics: { enabled: false, ga4: false, clarity: false, consentRequired: true },
```

例外：**`analytics` 建议第一天就开**。它不增加任何用户门槛，而且是你判断
"什么时候该打开付费"的唯一依据。

## 四、换掉图片

`public/` 下：图标、Open Graph 分享图。

用 `next/image` 而不是 `<img>`，并且必须写死宽高或固定宽高比——否则页面加载时
会跳动，性能闸门（CLS ≤ 0.1）过不了。

## 五、换配色和样式

用的是 Tailwind CSS v4，**没有 `tailwind.config.js`**，全部配置在 CSS 里。
`src/app/globals.css` 很短，只有三段：引入 Tailwind、设计 token、几条基础样式。

### 换配色：只改一个地方

配色是 `:root` 上的一组语义变量，深色模式在 `@media (prefers-color-scheme: dark)`
里覆盖同一组名字。改配色只需要改这两块的值：

```css
:root {
  --background: oklch(0.99 0.002 265);   /* 页面底色 */
  --foreground: oklch(0.21 0.012 265);   /* 正文字色 */
  --surface: oklch(1 0 0);               /* 卡片底色 */
  --surface-muted: oklch(0.97 0.004 265);/* 次级区块底色 */
  --border: oklch(0.91 0.006 265);       /* 描边 */
  --muted: oklch(0.52 0.014 265);        /* 次要文字 */
  --accent: oklch(0.53 0.19 265);        /* 主色（按钮、链接）*/
  --accent-hover: oklch(0.47 0.19 265);
  --accent-foreground: oklch(0.99 0.002 265); /* 主色上的字 */
  --inverse: oklch(0.19 0.012 265);      /* 反色区块 */
  --inverse-foreground: oklch(0.97 0.004 265);
  --ring: oklch(0.53 0.19 265);          /* 键盘聚焦框 */
}
```

颜色用的是 `oklch(亮度 彩度 色相)`。**最省事的换色办法：只改最后那个色相数字**
（265 是蓝色），三个数一起动容易调崩对比度。常用色相：0 红、30 橙、140 绿、
265 蓝、300 紫。

**深色模式那块要一起改**，否则浅色换了深色还是旧的。

字号和字体也在 `@theme inline` 里：`--font-sans` 换字体栈，`--text-display`
换首页大标题字号。

### 写组件时不要直接写颜色

⚠️ **永远用语义类名，不要用 Tailwind 的原始色**：

```tsx
// 对
<div className="bg-surface text-foreground border-border">

// 错 —— 深色模式下会瞎掉
<div className="bg-white text-gray-900 border-gray-200">
```

可用的语义类：`bg-background`、`bg-surface`、`bg-surface-muted`、`bg-inverse`、
`text-foreground`、`text-muted`、`text-accent`、`border-border`。

### 常用样式串已经写好了

`src/components/ui/styles.ts` 里是一堆导出的字符串常量（不是组件，所以**零运行时
JS**）。直接引用，别重新拼 utility：

```tsx
import { container, card, buttonPrimary, bodyText } from "@/components/ui/styles";

<div className={container}>
  <div className={card}>
    <p className={bodyText}>……</p>
    <button className={buttonPrimary}>开始</button>
  </div>
</div>
```

有这些：布局 `container` / `containerNarrow` / `sectionSpacing`；
文字 `eyebrow` / `pageTitle` / `sectionTitle` / `subTitle` / `cardTitle` /
`bodyText` / `leadText` / `metaText`；容器 `card` / `panel`；
按钮 `buttonPrimary` / `buttonSecondary` / `buttonDanger` / `buttonGhost` /
`buttonPrimaryLarge` / `buttonSecondaryLarge` / `buttonOnInverse`；
表单 `label` / `input` / `inlineLink`；列表 `listDivided` / `listRow`。

同一种写法出现第三次时，往这个文件里加一个新常量，别到处复制。

### 改完必须自己打开看

**没有任何自动检查能发现页面变难看了。** e2e、性能、无障碍测试在一个布局
完全崩掉的页面上照样全绿——它们只验 DOM 结构、元数据和预算，不看长相。

改完样式：`bun run build` 然后开浏览器逐页看。

## 六、写产品代码

放 `src/modules/<产品名>/`：

```
src/modules/my-tool/
  domain/      纯逻辑，不碰 React 和数据库
  ui/          React 组件
  index.ts     对外唯一入口
```

有两条边界由 lint 强制，违反了直接报错：

- 模块内**不能** import `@/config/*`（配置要引模块，反过来会成环）
- 外部**只能** import `@/modules/my-tool`，不能深入内部文件

细节见[产品模块](参考/产品模块.md)。

## 七、上线前的检查

### 本地跑一遍

```bash
bun run verify:seo        # SEO 闸门
bun run verify:i18n       # 多语言完整性
bun run verify:security   # 安全头
bun run build             # 能不能构建
```

### SEO 闸门会拦你什么

这些都会导致失败，提前知道能省时间：

- 标题/描述/H1 缺失、重复，或者还留着 `TODO`、`placeholder` 之类的词
- 页面内容和声明的 `searchIntent` 明显不符
- 有页面从首页点不到（孤儿页）
- 内链指向不存在的路由
- 锚文本是 "click here"、"read more" 这种没信息量的词
- URL 层级太深
- 生产环境下还有页面标着未审阅

### 把两个 draft 改成 reviewed

```
src/config/seo.config.ts    releaseStatus: "draft" → "reviewed"
src/config/legal.config.ts  releaseStatus: "draft" → "reviewed"
```

**在填完真实法律信息之前不要改。** 这个拦截是故意的——防止你带着一份写着
"Sample Operator" 的隐私政策上线。

改完跑：

```bash
bun run verify:release --mode=production
```

## 八、部署

1. GitHub 仓库连到 Vercel
2. Vercel 环境变量里配 `APP_ORIGIN`（真实域名）和 `DATABASE_URL`
3. 域名解析指向 Vercel
4. 部署

环境映射是自动的，不用手工设 `APP_ENV`：

| Vercel 环境 | APP_ENV | 会被搜索引擎收录吗 |
|---|---|---|
| Development | local | 否 |
| Preview | staging | 否 |
| Production | production | **是** |

**只有 production 会输出 canonical、sitemap 和可索引标记。** 本地和预览环境
一律 noindex——所以你在本地访问 `/sitemap.xml` 看到 404 是正常的，不是 bug。

## 九、提交给 Google

域名上线后：

1. Google Search Console 验证域名归属
2. 提交 `https://你的域名/sitemap.xml`
3. 用「网址检查」看首页和重点页面
4. 等。收录通常要几天到几周

## 十、以后打开付费和登录

三个档位，按需要推进：

### 第 1 档（上线时）
SEO + 法律页 + analytics。零门槛，用户直接用。

### 第 2 档：加登录
需要留存用户数据时：

```ts
auth:  { enabled: true, magicLink: true, google: false, password: false },
email: { enabled: true },
```

然后配 `RESEND_API_KEY`、`EMAIL_FROM`、`BETTER_AUTH_SECRET`、Turnstile 密钥。

登录方式只有两种：**邮件魔法链接**和**谷歌登录**。
密码登录被永久禁用了（类型层面就是 `false`，改不了）。

### 第 3 档：加支付

```ts
commerce: { enabled: true, oneTime: true, subscriptions: false, credits: false },
```

**注意一个硬约束：支付必须配合登录。** 结账接口写死了要登录态
（`checkout/route.ts` 里 `if (!account) return 401`），所以打开支付的那天，
必须同时开着 `auth` 和 `email`。

产品定义在 `products.config.ts`：

```ts
{
  key: "starter-pack",
  version: 1,                    // 版本不可变，改价格要加新版本
  commercialModel: "one_time",   // 或 "subscription"
  currency: "USD",
  expectedPrice: "29.00",
  providerProductIdByEnvironment: {
    test: "Waffo 测试环境的商品 ID",
    production: "Waffo 正式环境的商品 ID",
  },
  fulfillmentKey: "starter-pack",
  refundPolicyKey: "default-one-time",
}
```

**每个 `fulfillmentKey` 都必须有人认领。** `fulfillment.config.ts` 里的处理器表
出厂是空的，而 `order-fulfillment.ts` 在表里查不到 `fulfill:<fulfillmentKey>`
会直接抛异常——结果是钱收了、履约任务一路重试到死信。最省事的认领方式是用积分：
在 `credits.config.ts` 里加一条，运行时由 `commerce-runtime.ts` 自动注入，
不需要新的数据库迁移。

```ts
export const creditFulfillmentDefinitions = [
  {
    fulfillmentKey: "starter-pack",   // 和商品里那个必须一模一样
    creditType: "lookup",
    quantity: 100,
    expiresAfterDays: 365,
  },
] as const satisfies readonly CreditOrderFulfillmentDefinition[];
```

#### 本地把整条链路真跑一遍

支付是唯一一个"读代码判断不了对不对"的模块——收到一次真实 webhook 才算通。
全程是测试模式，刷不出真钱：`commerce-runtime.ts` 写死了只有
`APP_ENV=production` 才连 Waffo 生产环境。

**1. 起隧道，把公网地址写进 `APP_ORIGIN`。**

```bash
brew install cloudflared
cloudflared tunnel --url http://localhost:3000
# 把打印出来的 https://xxx.trycloudflare.com 填进 .env.local 的 APP_ORIGIN
```

`APP_ORIGIN` 必须和浏览器地址栏完全一致，否则结账接口按 `origin` 不匹配返回
403。cloudflared 每次重启都换域名，换了就得改 `.env.local` 并重启服务。
本地测试不需要真实域名和 HTTPS 证书，也不需要 `WAFFO_CONTRACT_VERIFIED=1`
（那个只在 `APP_ENV=staging|production` 时强制）。

**2. 用生产构建，不要用 `bun run dev`。** dev server 的 HMR websocket 过隧道会
502，客户端水合停在半路，所有 `useEffect` 都不跑。表现很有迷惑性：页面看着正常，
但登录按钮一直是灰的，像是 Turnstile 坏了。`bun run build && bun run start`
没有这个问题。

**3. 把 webhook 指到隧道上。** 不用开 Waffo 后台，SDK 就能改：

```ts
await client.webhooks.add({
  storeId: process.env.WAFFO_STORE_ID,
  channel: "http",
  url: `${process.env.APP_ORIGIN}/api/webhooks/waffo`,
  events: ["order.completed", "refund.succeeded", "refund.failed"],
  testMode: true,
});
```

**4. 走一遍：** 注册登录 → 首页点购买 → Waffo 收银台用 Quick Fill 里 Visa 那行的
「Success」→ 付款。

**5. 查库。四件事都要对，少一件就是链路没通：**

```sql
select status, paid_at from orders;                       -- paid
select status, amount_minor from payments;                -- succeeded
select operation, state, attempts from fulfillment_jobs;  -- completed
select credit_type, quantity, state from credit_grants;   -- 数量对上、active
```

履约是 webhook 落库时同步做的，不用等 cron 敲门。

**`verify:commerce` 看不见积分履约。** 它只认 `fulfillment.config.ts` 里的静态表，
而积分处理器是运行时注入的，静态表里永远没有；它还要求每个启用商品都填了
`production` 的 provider 商品 ID。所以"只有测试商品 + 用积分履约"这套组合运行时
完全正常，却必然过不了这道闸门。正式上线前本来就要在 Waffo 生产环境建好商品，
那时把 production ID 补上即可——在那之前这道闸门失败要人工判断是不是这个原因，
不要当成运行时坏了去改代码。

## 十一、真实会踩的坑

这些是实际建站时撞到的，文档里其他地方没写：

**改了 `routes.config.ts` 忘了改 `seo-landings.config.tsx`** —— 后者顶部的
`indexableRoute("/xxx")` 会因为路由不存在直接抛错。两个文件必须一起改。

**本地看不到 sitemap** —— `/sitemap.xml` 在非 production 下返回 404，这是设计
行为不是 bug。想验证的话用 `bun run verify:seo:production`。

**纯 SEO 站也要 DATABASE_URL** —— 环境变量校验里是必填项，但实际不查库，
本地填占位串就行。

**改样式时顺手改了文案会挂测试** —— e2e 测试按按钮文字定位元素。
改 CSS 就只改 CSS。

**没有任何检查能发现页面长得难看** —— 所有闸门查的是 DOM 结构、元数据和性能
指标，没有一个看视觉。改完 UI 一定要自己打开浏览器看一眼。

**`reviewStatus: "reviewed"` 必须配一个 `reviewFingerprint`** —— 只写前者，
`createRouteRegistry` 会抛"missing fingerprint"，而它是在 `routes.config.ts`
模块顶层调用的，于是**所有** import 这个文件的闸门一起挂掉，报错看起来和 SEO
无关。指纹是路由那几个字段的哈希，改了标题描述就得重算：临时把这几条改成
`reviewStatus: "draft"` 让文件能 import，跑一个一次性脚本打印
`seoReviewFingerprint(route)`，再把值填回去。这也是设计意图——改了文案就等于
之前的人工审阅作废了。

**`COMMERCE_RETENTION_KEY` 必须正好是 32 字节的 base64** —— 长度不对的话环境
校验直接抛错，站点每个页面都 500，而错误信息藏在服务端日志里，浏览器只看到
一片 500。用 `openssl rand -base64 32` 生成，别手搓。

**`drizzle.config.ts` 不读 `.env.local`** —— 它直接取 `process.env.DATABASE_URL`。
跑迁移得把变量写在命令行前面：`DATABASE_URL=... bun run db:migrate`。
Next.js 自己（dev 和 start）是会读 `.env.local` 的。

**删了路由之后 `.next` 里的旧类型文件会造出一堆假报错** —— typecheck 会指着
根本不存在的路由报十几条错。`rm -rf .next` 再跑。

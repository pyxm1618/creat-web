# 产品代码放哪里

这个模板给的是产品**外面那一圈**——SEO、路由、法律页、登录、支付、积分——但不包括产品本身。时区规划器、计算器、生成器：那是你自己的代码，它需要一个不会腐蚀"下个站还想复用的那部分"的位置。

那个位置是 `src/modules/<产品名>/`。

## 为什么不能放别处

四个看起来都行的位置，各有各的代价：

| 位置                    | 会坏掉什么                                                                                                              |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `src/config/*.config.tsx` | `tool-demo` 区块接受一个 `ReactNode`，塞个小组件是能塞进去。但真正的产品代码会把配置文件变成应用文件，配置就不再是"扫一眼能审完"的东西了。 |
| `src/components/`       | 这些是把配置渲染成页面的渲染器。产品逻辑放这里会抹掉"渲染器"和"产品"的界线，而且平台代码本来就被禁止依赖它。                  |
| `src/platform/`         | 这是可复用的那一半。产品逻辑放这里，意味着你下一个站会继承上一个站的业务规则。                                              |
| `src/modules/`          | 不坏任何东西。就是这里。                                                                                                  |

`eslint.config.mjs` 一直禁止平台代码 import `@/modules/*`，所以这条边界比目录本身还早存在。

## 目录结构

```
src/modules/<产品名>/
  domain/      纯逻辑 —— 不含 React、不做 IO、不碰数据库
  ui/          React 组件，服务端或客户端都行
  index.ts     公开入口；外面唯一可以 import 的文件
```

`domain/` 和 `ui/` 是建议，不是规矩——小模块一个 `index.ts` 就够了。**公开入口是规矩，而且有 lint 强制。**

## 依赖方向

| 边                                   | 允许 | 由谁强制                  |
| ------------------------------------ | ---- | ------------------------- |
| `platform` → `modules`               | ✗    | `no-restricted-imports`   |
| `modules` → `config`                 | ✗    | `product-module-boundary` |
| 外部 → `modules/<p>/内部文件`        | ✗    | `product-module-boundary` |
| 外部 → `@/modules/<p>`               | ✓    | —                         |
| `modules` → `platform`               | ✓    | —                         |
| `modules` → `components/ui/styles`   | ✓    | —                         |
| `config` → `modules`                 | ✓    | —                         |
| `app` → `modules`                    | ✓    | —                         |

两条禁令是承重的：**配置负责组装模块，所以模块反过来 import 配置会形成循环**；而所有外部 import 都走 `index.ts`，是为了让你以后能随意重排模块内部而不动别处。

一个模块伸手进**另一个**模块的内部，出于同样理由被拒——走对方的公开入口。

## 怎么接到首页上

`index.ts` 导出对外的那一面：

```ts
// src/modules/planner/index.ts
export { PlannerSurface } from "./ui/planner-surface";
export type { PlannerProps } from "./ui/planner-surface";
```

配置负责组装：

```tsx
// src/config/home.config.tsx
import { PlannerSurface } from "@/modules/planner";

{
  type: "tool-demo",
  heading: "找出团队的共同工作时段",
  body: "…",
  surface: <PlannerSurface />,
}
```

文案和区块顺序仍归配置管，行为归模块管。两个文件都不会长进对方里去。

## 服务端、客户端和 CSP

`src/proxy.ts` 会给每个请求发一个 nonce，CSP 对脚本不放行任何 `unsafe-inline`。把对 SEO 重要的部分保持服务端渲染，只给交互的叶子节点标 `"use client"`——模板其余部分就是这么切的。

交互式产品代码会计入 `tests/performance/marketing-performance.spec.ts` 里的脚本预算（350 KB、20 个文件），目前整棵树用掉的还不到一半。

任何碰数据库或密钥的东西都属于 `domain/`，放在服务端边界后面，通过 route handler 或 server action 访问，**绝不能被打包进客户端组件**。

## 强制手段

`tests/unit/architecture/product-module-boundary.test.ts` 证明这条规则会拒绝 config import、深层 import 和跨模块内部访问，同时放行平台调用、共享样式和公开入口。`bun run verify:architecture` 会对整棵树跑一遍。

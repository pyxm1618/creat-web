# 扩展与升级

两件以后才会做、但做的时候必须按规矩来的事：从模板拉取更新，和接入新的支付商。

---

# 一、已有产品怎么拉取模板更新

用 `creat-web` 建出来的产品是**你自己的代码库**，不是模板的活实例。不要把模板整个 merge 覆盖到产品的配置和内容上。

## 1. 记录基线

在产品仓库里记下：它是从模板的哪个版本/commit 建出来的，以及要升到哪个版本。对比这两个版本之间的 `CHANGELOG.md`。

## 2. 给每条模板改动分类

对每条安全/平台改动，记录：

- 涉及哪些平台文件/模块；
- 数据库迁移，以及它是增量的还是破坏性的；
- 新增/删除/改名的环境变量；
- 服务商后台需要改什么；
- 配置接口有没有变；
- 验证命令和预期证据；
- 回滚要求；
- 这条改动是**安全必须**还是可选功能。

产品自己的文案、路由、法律事实、服务商 ID、定价和功能选择，**不会因为模板变了就该被覆盖**。

## 3. 有意识地移植

模板的某个 commit 如果是孤立的且能干净应用，优先用 cherry-pick。否则手工移植最小的一段连贯改动。**绝不要靠"冲突时无脑选模板那边"来解决产品配置/内容的冲突。**

迁移按顺序应用。如果某个迁移或服务商改动不可逆，先在隔离的恢复库上演练一遍再上生产。

## 4. 对齐配置

`.env.example`、功能/配置类型、部署密钥要一起更新。新增的必需密钥都是**专用**的——绝不要把登录、cron、webhook、加密、数据库或服务商的密钥挪作他用。

## 5. 验证

至少跑这些：

```bash
bun install --frozen-lockfile
bun run format:check
bun run lint
bun run typecheck
bun run test:unit
TEST_DATABASE_URL="$TEST_DATABASE_URL" bun run test:integration
bun run test:contract
bun run db:verify
bun run verify:security
bun run verify:secrets
bun run build
bun run test:e2e
bun run verify:release
```

外加对应 changelog 条目里点名的命令。涉及安全、积分、支付、订阅、留存或迁移的改动，还要跑各自的专项套件。

## 6. 发布与回滚

先部署到隔离的 staging。验证迁移、登录、任务、服务商回调和产品主流程。在新版本被证明可用之前，保留上一个部署和数据库恢复点。需要回滚时按 [故障处理](../运维/故障处理.md) 走。

## 7. 结束升级记录

记录：来源版本/commit、目标版本/commit、移植了哪些 commit/文件、迁移、环境/服务商改动、验证结果、staging 证据、生产部署，以及任何**有意推迟**的可选改动。

# 二、接入新的支付商（比如 Stripe）

## 目标

新支付商必须作为**适配器**接入，而不是第二套交易架构。订单、支付、订阅、退款、权益、积分、持久化任务和对账，全部保持与服务商无关。

## 稳定边界

实现 `src/platform/commerce/application/payment-provider.ts` 里的 `PaymentProvider`。

适配器只管服务商这一侧：

- 服务商认证 / 客户端构造；
- 创建结账；
- 服务商的客户会话或等价授权；
- 订阅取消/恢复命令；
- 提交退款；
- 支付查询/对账事实；
- 验签；
- 把服务商载荷映射成 `NormalizedProviderEvent`。

适配器必须显式声明自己的能力。**应用层/领域层代码不得根据服务商的类名或事件载荷做分支判断。**

## 权威归属

适配器**不**拥有：

- 商品定价权；
- 本地订单 ID；
- 留存的账户主体；
- 订阅宽限期政策；
- 退款累计上限的强制；
- 权益/积分回收政策；
- 持久化重试/死信语义；
- 运维对账历史。

这些留在本地的配置/领域/应用/数据库层。

## 结账

`createCheckout` 收到的是**服务端拥有的商品快照**。不接受来自浏览器的价格/金额权威。

只返回稳定的服务商标识和一个 HTTPS 结账 URL。不要把任意服务商结账载荷持久化进领域层。

## Webhook

适配器必须：

1. 在信任任何载荷字段之前，对**精确的原始请求体**验签；
2. 在服务商支持的前提下，验证环境/账户/店铺身份；
3. 归一化服务商事件 ID 和时间戳；
4. 只映射本地领域需要的、已验证的字段；
5. 对本地领域有意忽略的合法事件返回 `unsupported_signed_event`；
6. **绝不**把浏览器或 webhook 到达顺序当成本地幂等性的依据。

Webhook 收件箱存的是最小化的归一事实加哈希/留存元数据，它不是服务商 JSON 的永久档案。

## 订阅

把服务商的订阅语义映射到已有的本地归一事件/状态投影上。服务商特有的状态可能需要一张显式映射表，但**不要**把服务商状态直接加进领域代码，除非它确实代表一个与服务商无关的生命周期状态。

本地计费周期（`month` / `year`）来自不可变的商品快照，不是从 webhook 里顺手解析出来的。

本地的逾期宽限截止时间是产品政策，**适配器不得延长或重算它**。

## 退款

`requestRefund` 提交的是一个**已经本地授权过**的退款请求。应用层已经对该笔支付做过串行化，并强制过"已捕获 / 已退 / 在途请求"的上限。

把服务商的退款/工单 ID 映射到 `externalRefundReference`。服务商返回"请求已接受"**不等于**退款已结算，除非服务商合约明确保证该状态；否则以签名事件或对账为准。

部分退款是服务商能力，但权益回收政策仍归本地/产品。

## 对账

用服务商 API 实现 `getPayment`（未来只在领域确有需要时才加与服务商无关的对账方法）。返回归一化事实，而不是服务商对象。

当服务商给不出足够无歧义的事实时，**失败关闭**（fail closed），交给运维对账，而不是自己编一个状态出来。

## 上线前必须有的测试

- 针对精确锁定的 SDK/API 版本的适配器合约测试；
- 用精确原始请求体做的验签回归测试；
- 环境/账户身份不匹配的拒绝测试；
- 服务端拥有价格/金额的断言；
- 结账 URL 校验；
- 每个支持事件的 webhook 归一化测试；
- 走公共应用路径的重复事件幂等测试；
- 退款/订阅命令幂等测试；
- 该服务商功能**关闭**时的构建/运行测试，证明不需要任何该服务商的密钥或 SDK 初始化；
- 构建矩阵、集成、安全和发布门禁。

关键的服务商依赖要精确锁版本。**不要**在接入服务商的同时顺手做一次全局依赖升级。

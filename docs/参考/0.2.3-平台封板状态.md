# 0.2.3 平台封板状态

**封板日期：2026-09-06**  
**运行时代码基线：`67f004c68ae538acb89ae171972306780b19e6d7`（PR #19 合并后）**

这份文档只记录 `creat-web` 平台本身的最终验收边界，避免后续会话把已经关闭的问题重新变成“上线前必须继续开发”的门禁。具体网站仍需完成自己的商品、域名、法律文本、Production 密钥和服务商资源配置。

## 最后一次真实退款验收事实

最终验收使用一个全新的 Waffo Test Mode 一次性商品和全新的支付样本：

1. USD 1.88 Test payment 成功；本地订单/支付进入 `paid` / `succeeded`。
2. 真实签名 webhook 被应用，履约完成，`usage=100` credits 正常发放。
3. 对该支付只发起 **1 次**全额退款 provider write。
4. 该 write 的应用侧结果为 `ambiguous`。
5. 随后的已认证只读 provider reconciliation 返回：`refundTickets=0`、`refunds=0`。
6. 本地退款正确保持 `reconciliation_required`；没有第二次退款 POST，没有伪造 webhook，没有手工 DB settlement，也没有错误撤销 credits。
7. 订单因此保持 `paid`，100 credits 保持有效。

这证明的是：**在 provider 写入结果无法确认时，0.2.3 会失败关闭并阻止重复退款。**

它**没有**证明 Waffo 的真实退款成功链路已经在 Test Mode 或 Production 跑通，因此不得把“自动退款成功 E2E”写成 PASS。

## Waffo 限制的处理边界

本次最终状态固定为：

> `REFUND PLATFORM SAFETY: PASS`
>
> `REAL REFUND E2E: BLOCKED BY WAFFO TEST MODE REFUND-CREATE PROVIDER BEHAVIOR`
>
> `NO FURTHER REFUND RETRIES RECOMMENDED`

如果 Waffo Test Mode 再次出现“退款 POST 已发出一次，但查询不到 ticket / refund”的情况，不允许通过第二次 POST、人工绑定 provider ID、伪造 webhook、手工修改金融投影或反复创建新支付来把验收结果做绿。

未来只有当 Waffo 明确修复/解释该行为，或提供可验证的成功退款事实后，才需要重新跑一次真实退款成功 E2E；届时应沿用 0.2.3 的 one-shot write、provider read、replay-safe settlement 规则，而不是重写退款基础设施。

## 具体网站上线时的边界

平台可以继续用于实际建站和上线，但必须区分“平台能力存在”与“某个网站的自动退款已经 Production 验证”：

- 一次性支付、订阅、履约、credits 等仍需用该网站自己的真实商品/商户/域名配置完成上线检查。
- 在 Production 真实退款成功链路尚未独立验证前，不应对用户宣称应用内自动退款已经 Production-verified。
- 需要上线退款政策时，可以采用明确的人工/运营处理兜底；这属于具体网站的运营策略，不是重新打开 starter 平台开发的理由。
- 临时 `trycloudflare.com` tunnel 只用于本地/Test E2E；正式网站必须使用自己的稳定 HTTPS 域名和对应 webhook endpoint。

## 什么时候允许重新打开平台

只有以下情况之一出现，才重新修改 `creat-web` 平台：

1. 在最新 `main`、正确 migration 和正确配置下出现**可复现的 creat-web 逻辑错误**；
2. 发现安全漏洞或可能造成资金/权益错误的确定性缺陷；
3. 一个真实下游产品明确需要当前 starter 不具备的新能力；
4. Waffo provider 合约/行为发生变化，需要对现有适配器做确定性的兼容调整。

下面这些**不是**重开理由：

- “还能再多防一种理论 edge case”；
- 为了把 Test Mode refund E2E 做绿而重复创建 payment/refund；
- 没有新证据时继续增加 reconciliation 层；
- 把 provider limitation 当成平台未完成；
- 为了文档收口再次 bump 模板版本。

## 最终改动归属

- PR #19 以及之前的平台运行时代码、migration、测试和 0.2.3 版本变更均已进入 `main`。
- 最终 E2E 使用的 one-time 商品/100-credit 配置属于**临时验收配置**，验收后已恢复，不应提交进通用 starter。
- 本地执行 migration 是运行环境状态；migration 源文件已经随 0.2.3 进入仓库，不需要额外提交数据库状态。
- Test webhook / tunnel 是外部运行环境配置，不属于 Git 仓库；临时 tunnel 停止后其 URL 失效是预期行为。
- 最终验收 worktree 没有留下平台代码改动。原始 checkout 若本来存在用户自己的 dirty changes，不属于本次封板工作，也不应被自动覆盖或提交。

## 封板规则

`0.2.3` 是当前接受的平台基线。后续建站默认从这个基线继续做**具体产品**，而不是继续优化 starter 本身。没有上述重开条件时，平台工作视为完成。

# v0.1.0 staging activation verification

This document separates repository-complete controls from deployment facts that require real external resources. Do not mark staging or production activated merely because repository CI is green.

## External resources required before staging activation

Record the actual owner and environment for each item. Never paste bearer secrets into this document.

- [ ] Real staging domain and Vercel project, isolated from production.
- [ ] Real staging PostgreSQL database with backup/PITR capability and retention confirmed.
- [ ] Reviewed legal operator identity, jurisdiction, support address, privacy/terms/acceptable-use/refund/account-deletion text.
- [ ] Google OAuth staging client with exact origin and callback configuration, if Google sign-in is enabled.
- [ ] Resend staging API key, verified sender/domain and support mailbox, if email is enabled.
- [ ] Waffo staging/test merchant, store, products/prices, private credential and webhook verification material, if commerce is enabled.
- [ ] Cloudflare Turnstile staging widget/site key and secret, with expected staging hostname.
- [ ] GA4 and/or Clarity staging destinations only if analytics is enabled, with consent/privacy review.
- [ ] A real alert receiver/on-call channel wired to structured `operational_alert` events.
- [ ] Search Console property/domain verification when the production SEO launch is ready; do not submit draft/staging URLs.
- [ ] Production IndexNow ownership key when IndexNow is enabled. Do not use staging URLs as search-submission evidence.
- [ ] Human-reviewed translations for every locale advertised as supported. Do not machine-copy English merely to create locale routes.

## Deployment configuration gate

- [ ] `VERCEL_ENV=preview` maps to `APP_ENV=staging`; `APP_ENV=test` is rejected on Vercel.
- [ ] `APP_ORIGIN` is the exact HTTPS staging origin.
- [ ] Secrets are purpose-specific; auth, cron, database, Waffo, Turnstile, retention encryption and provider credentials are not reused.
- [ ] Turnstile uses real staging keys; Cloudflare test keys are rejected by staging runtime config.
- [ ] Test mailbox transport is absent; Resend is used when staging email is enabled.
- [ ] Waffo contract verification flag is set only after merchant/store/webhook resources are validated.
- [ ] Analytics is disabled unless the approved destination IDs and consent policy are configured.
- [ ] If IndexNow is configured, `INDEXNOW_KEY` passes the documented format gate and `CRON_SECRET` protects the internal submission endpoint; the public IndexNow key is not reused as internal authentication.

## Database and recovery drill

- [ ] Run migrations against the isolated staging database.
- [ ] Confirm `/api/health/ready` returns `ready` without exposing connection details.
- [ ] Create a provider snapshot/PITR restore into a **second isolated database/project**.
- [ ] Run `RESTORED_DATABASE_URL=... bun scripts/verify-restored-database.ts` against that restored database.
- [ ] Record source recovery timestamp, restore duration, migration count, verifier result and cleanup; do not record private row contents.
- [ ] Confirm the restored database is never targeted by production/staging webhooks or scheduled workers during the drill.

The repository CI performs the same dump/restore/verifier flow against synthetic PostgreSQL data. The staging drill proves the real database provider's backup/PITR configuration rather than replacing the repository test.

## Credential rotation drill

Choose at least one disposable staging credential and execute the matching section of `docs/runbooks/key-rotation.md`.

- [ ] Create replacement credential.
- [ ] Deploy/cut over using the documented overlap or maintenance procedure.
- [ ] Verify the dependent journey.
- [ ] Verify rollback/recovery path without reusing a compromised credential.
- [ ] Revoke the old credential.
- [ ] Record only credential purpose/key identifier and evidence, never secret material.

Review the procedures for Better Auth, Google, Resend, Waffo API/private credential, Waffo webhook verification, Turnstile, cron/internal jobs, database credentials and analytics destinations even if only one disposable credential is actually rotated in the drill.

## Authentication and abuse controls

- [ ] Magic Link renders Turnstile and cannot submit before challenge completion.
- [ ] Valid challenge permits a request; forged/expired/replayed challenge is rejected.
- [ ] Action and hostname mismatch are rejected.
- [ ] Magic Link remains scanner-safe and single-use.
- [ ] Durable email/IP rate limits work across requests and do not reveal account existence.
- [ ] Google OAuth state/callback/redirect behavior is verified when enabled.
- [ ] Sensitive pages and auth endpoints are `no-store` and `noindex`.

## Commerce, subscription and credits

If commerce is enabled:

- [ ] Test checkout uses the staging/test merchant and the exact configured product IDs/prices.
- [ ] Valid signed webhook is accepted and duplicate delivery is idempotent.
- [ ] Invalid signature stores no raw payload.
- [ ] Known successful events retain no raw payload; transient/unresolved retention follows configured limits.
- [ ] Multiple workers can process/purge without duplicate claims.
- [ ] Subscription cancel/resume/grace/terminal transitions are verified against the provider's test environment.
- [ ] Refund initiation and provider-settlement reconciliation are verified; uncertain provider outcomes go to reconciliation/operator review rather than direct state patching.
- [ ] One-time and subscription credit fulfillment is idempotent.
- [ ] A reservation made before source-grant expiry can commit after expiry.
- [ ] Release/stale-expiry after source-grant expiry does not restore spendable balance.

## Jobs, metrics, alerts and dead letters

- [ ] Vercel schedules invoke only `/api/internal/jobs/{commerce,reconcile,credit-expiry,account-deletion}` as configured.
- [ ] Missing/wrong Bearer credential receives `401`; the secret is never accepted through a query string.
- [ ] Batch and runtime bounds are visible in job behavior/logs.
- [ ] Concurrent workers do not double-claim leased work.
- [ ] Structured metrics contain no user/order/payment/session identifiers.
- [ ] Trigger and receive test alerts for: dead letter creation, Magic Link spike, invalid webhook-signature spike, reconciliation mismatch, stale/backlogged jobs and repeated provider failure.
- [ ] `scripts/inspect-dead-letters.ts` shows only redacted metadata.
- [ ] A synthetic staging dead letter is requeued with `scripts/retry-dead-letter.ts`, requiring environment/id/reason/confirm and leaving an immutable audit event.

## SEO, privacy and performance

- [ ] Production-mode browser verification passes with the intended canonical origin; test-mode `noindex` behavior is not used as production evidence.
- [ ] Public indexable pages emit correct canonical/title/description/robots and expected sitemap membership.
- [ ] Private/legal/system route indexing rules match the route registry.
- [ ] Script CSP does not rely on `unsafe-inline`; Turnstile/provider origins are explicit.
- [ ] Consent is absent from required product functionality: deny persists, settings can be reopened, consent can be withdrawn, and analytics stops after withdrawal.
- [ ] Analytics event payloads contain only allowlisted non-sensitive properties.
- [ ] Real-page performance budgets remain within the repository gate after provider activation.
- [ ] If IndexNow is enabled in production, `GET /indexnow-key.txt` returns the configured key as plain text from the canonical host.
- [ ] Missing or wrong Bearer credentials cannot call `POST /api/internal/seo/indexnow`.
- [ ] Submit only a genuinely recent production URL change (new, updated, deleted, moved, or redirected), never the staging site or an unchanged full sitemap batch.
- [ ] Record the changed canonical URL, submission time, and accepted provider HTTP status (`200` or `202`) without recording `CRON_SECRET` or other private credentials.
- [ ] Keep `/sitemap.xml` submitted/available as the complete URL inventory; IndexNow is an incremental change notification, not a sitemap replacement.

## Release decision

Repository completion and staging activation are separate states:

- **Repository complete:** all code, tests, runbooks, clean-setup proof, restore proof and CI gates pass without requiring private production resources.
- **Staging activated:** every applicable external-resource checkbox above has real evidence.
- **Production ready:** staging activation is complete, production legal/domain/provider/search/alert resources are confirmed, production-mode SEO/security checks pass against the intended origin, and rollback/restore ownership is assigned.

Until external activation is complete, keep the PR/release record explicit about the blockers rather than weakening configuration or replacing missing facts with placeholders.
